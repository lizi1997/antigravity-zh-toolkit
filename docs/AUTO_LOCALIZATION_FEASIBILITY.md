# Antigravity 自动汉化：可行性最终报告

> 面向对象：项目维护者。回答一个问题：**「有没有 100% 完美的自动汉化方案？」**
>
> 上游材料：`docs/auto-localization-baseline.md`（现状与可达域）、`docs/auto-localization-design.md`
> （端到端设计）、`docs/auto-localization-mvp.md`（原型范围）、`docs/auto-localization-verification.md`
> （独立验证）、`docs/auto-localization-review.md`（独立评审，结论 PASS）。
>
> 报告时间：2026-11-24（Asia/Taipei）。本文所有数字都标注了「实测」或「估算」；凡估算，一律不得转述为既成事实。

---

## 0. 一页结论

| 问题 | 回答 |
| :--- | :--- |
| 有没有 **100% 完美**（全 UI 中文 + 语义 100% 正确 + 零人工）的自动汉化方案？ | **没有。** 不是"还没做出来"，而是当前架构下**不可达**：有 4 条硬理由 + 13 条硬边界，其中 closed Shadow DOM / canvas / webview / 跨域 iframe / 原生系统对话框与菜单是**结构上不可达**。任何承诺"全 UI 100%"的方案都应在评审阶段被否决。 |
| 那能做到什么？ | **一条可重复、可度量、可回滚的自动化流水线**：机械段（QA / 合并 / 重建 / 回读 / 回滚 / 确定性）**已实测全自动**；翻译段**离线优先**（TM + 术语 + 规则模板，可选在线 LLM）；人工从「10 步里 8 步」压到「只做决策的 ≤2 步」。 |
| 现在能用吗？ | **能，但有边界**：`python scripts/localize.py release` 已是可用的 dry-run；`--apply` 已在隔离副本中验证语义，**真实仓库尚未 apply**（761 条候选原样保留，词典仍是 2,816 条）。 |
| 要多久？ | **Phase 2 离线纵切 + Phase 0 的基线门禁已完成**（Phase 0 仍有计数器/`restore` 回归欠账）；补齐 Phase 1（采集重写）+ Phase 2 尾巴（回填/规则）约 2–3 周（单人估算），之后 Phase 3/4/5 为可选与长期项。 |
| 一句话结论 | **工程上可行的是"自动化的汉化流水线"，不是"无人汉化"。** |

## 1. 直接结论：完美不存在，可达水平是多少

### 1.1 结论（分三层，请不要合并成一句"已经全自动"）

| 层 | 结论 | 强度 |
| :--- | :--- | :--- |
| **覆盖层** | 全 UI 100% 中文**不可达**（结构性），可达域内的静态界面当前约 **78.9%**，目标 **≥95%**；关键路径目标 **≥99% 且 P0 残留 0**（尚未真机实测） | 强（结构证据 + 实测盘点） |
| **质量层** | 语义准确率**不能被自动证明**，只能抽样；本轮 82 条抽样的**语义错误为 0**，但 95% 置信上限是 **3.6%**，不能外推成"零错误" | 中（单次抽样、单人判读） |
| **流程层** | 机械段（提案→QA→合并→重建→回读→回滚）已**可一条命令跑完且字节级可复现**；翻译段仍需人工提供译文（TM 覆盖不足） | 强（46 个测试 + 独立复算） |

### 1.2 可达水平（实测数字，全部可复算）

| 指标 | 实测值 | 口径 / 说明 |
| :--- | :--- | :--- |
| 候选 → 译文覆盖 | **761 / 761 = 100%** | 761 条译文本就写在同一份候选文件里（`file=761`），**不是机器翻译产出** |
| 免豁免通过门禁 | **759 / 761 = 99.7%** | 2 条被术语门禁 H10 拦下（内容问题，见 §6.3） |
| token 保真（占位符/URL/代码标识） | **12 / 12 = 100%**（全量独立复算丢失 0） | 含 token 的候选仅 12 条，样本小 |
| 术语合规 | **759 / 761 = 99.7%** | 同上 2 条 H10 |
| 人工抽样语义准确率 | **100%（0/82 语义错误）**，无瑕疵 **91.5%**（75/82） | 82/761 = 10.8% 抽样，单人判读，95% 上限 3.6% |
| QA 规则覆盖 | **15 / 23 = 65.2%**；blocker **10 / 13 = 76.9%** | 缺 H14–H20、H22（其中 H17–H20 属 `patterns.json` 范围外） |
| 词典规模变化（隔离副本） | 2,816 → **3,577（+27.0%）** | 副本演练，真实仓库**未 apply** |
| 机械段耗时 | dry-run **≈105 ms**；全量 apply（含重建+校验）**≈244 ms** | 独立验证报告实测（Windows 11 / Python 3.13）；本轮复跑 dry-run 同为亚秒级 |
| 幂等 / 确定性 | 二次 apply **0 新增**，词典/引擎/patcher sha256 不变；两个独立副本产物字节全等 | 验证报告在隔离副本实测；本轮未复跑 `--apply` |
| TM 命中率（真实数据） | **1 / 761** | ⚠️ 候选按定义就是词典里没有的串，所以这个数字天然低；**设计里的 60–85% 是估算、未实测**（见 §4 与 §6.4） |
| 片段类候选 | **55 / 761 = 7.2%** | 强片段信号；H13 只保证标点形态，**不保证拼接后通顺** |

### 1.3 为什么 100% 不可达（四条硬理由 + 五类结构边界）

| 理由 | 内容 | 证据 |
| :--- | :--- | :--- |
| **R1 表示不可达** | closed Shadow DOM（`element.shadowRoot` 返回 `null`）、canvas/图片文字（无 DOM 节点）、webview（独立渲染进程）、跨域 iframe（同源策略）、原生系统对话框/菜单（非 DOM） | `engine/engine_template.js` 只递归 `shadowRoot`；无 canvas/iframe/webview 代码；原生层只有 `menu.js`(2 组)/`updater.js`(2 组)/`main.js`(4 组) 字面量替换 |
| **R2 全集不可枚举** | 旧提取器在真实客户端产出 366,366 条候选 / 364,400 条"缺失"，真值约 752 条（SNR≈0.21%）；且服务端下发文案会随时新增 | baseline §2、§3（B6） |
| **R3 上下文单射不可判定** | 词典是 `key→value` 单射：`Save`（动词/名词）、`Cancel`、`Set up` vs `Settings` 在"一个英文串一个译文"的契约下无法根治 | `engine_template.js` 精确匹配 + 小写索引；抽样里已出现 `Set up → 设置` 与 `Settings` 同形 |
| **R4 质量不可自证** | 语义正确性需要人判断；本地门禁只能校验形式（占位符/术语/长度/片段形态） | 本轮 23 条规则中 8 条未实现，且已实现的规则也有子项缺口（RF-06） |

> 因此"完美"只能定义为：**在显式声明的可达域 D1–D4 内、以可复现方式达到 100%，并对域外给出不覆盖声明**。
> 域内当前未达 100%（78.9%），域外**永不**达 100%。

### 1.4 可达域（验收基线，沿用 baseline §4.2）

- **D1 静态界面**：主文档文本节点 + 11 个可译属性 + `input[type=button|submit|reset].value` + 开放 Shadow DOM → 目标 **≥95%**（二期 98%）。
- **D2 关键路径**：首启/引导、登录、设置-权限、对话与工具调用、审批弹窗、退出确认 → 目标 **≥99% 且 P0 残留 0**（**未实测**，需 Phase 4 探针）。
- **D3 动态文案**：180 条正则 + 自动生成的模板 → 目标：规则新增零回归。
- **D4 原生层**：已建立字面量映射的 8 组 → 只能逐条维护，随客户端升级漂移。
- **显式不覆盖**：B1–B6（closed Shadow DOM、canvas、webview、跨域 iframe、原生系统对话框/菜单、服务端下发）。

## 2. 推荐方案与不推荐方案

### 2.1 推荐：**离线优先 + 可选在线 LLM + 硬门禁 + 可逆**（design 方案 A）

| 组成 | 做什么 | 为什么必须这样 |
| :--- | :--- | :--- |
| 默认 provider = `tm`（本地翻译记忆 + 术语表 + 规则模板） | 零网络、零成本、确定性输出 | 保持 README 承诺的"零网络"；CI 可跑；供应链简单 |
| 可选在线 LLM | 双开关（`--allow-network` + `AG_L10N_ALLOW_NETWORK=1`）+ 脱敏 + 审计 + 预算 | 只在"新词、TM 未命中"时用；**当前是接口占位，任何情况下拒绝运行**，包内无网络 import |
| 硬门禁 | QA H1–H13/H21/H23（已实现）+ blocker 即 fail + `--waive` 留痕 | 让"机器提案"永远不能绕过结构校验进入词典 |
| 可逆 | pre-merge 备份 → 原子写 → 只经 `build.py` 重建 → 回读校验 → 失败自动回滚 | 最坏情况 ≤2 min 回到可用状态（客户端侧 snapshots 属 Phase 4） |
| 人工只做决策 | 术语冲突、片段语义、品牌词、规则审批 | 这些恰是 R3/R4 判定不了的 |

### 2.2 不推荐（以及为什么）

| 方案 | 为什么否决 |
| :--- | :--- |
| **纯在线 MT/LLM 全量机翻整包** | 破坏"零网络"承诺；每次发布要重新翻 3,000+ 条，成本与漂移不可控；无 TM/门禁时质量不可回归；且 **R1 决定的不可达区一条都覆盖不到** |
| **LLM 直写词典/直写正则** | 无确定性、无法回滚、无审计；术语与占位符风险高；`patterns.json` 正则一旦写错会影响整类文案（ReDoS / 误匹配） |
| **追求"全 UI 100%"的注入式方案**（OCR、closed Shadow DOM 打桩、webview 注入） | 成本高、破坏像素一致性、需要改宿主客户端；收益仅限边角区域；与"可逆、可审计"目标冲突 |
| **每次发布由人重跑旧提取器** | 已实测崩溃（孤立代理字符）+ SNR 0.21%，等于让人在 36 万条噪音里捞 752 条 |

### 2.3 取舍表（在线 / 离线 / 成本 / 周期 / 隐私）

| 维度 | 离线（默认，已实现） | 在线（可选，未实现） |
| :--- | :--- | :--- |
| 网络 | **0 出网**（有 socket 拦截测试） | 需双开关，仅开发机出网；客户端运行时仍 0 出网 |
| 质量 | 取决于 TM/人工；本轮真实数据 TM 只命中 1/761 | 理论更高，**但未实测**（设计估 60–85% 命中，属估算） |
| 成本 | 0 | 设计估算 **<$0.20/版**（752 条 × ~100 token，含重试） |
| 周期 | **已可用**（Phase 2 纵切） | 3–5 人日（含脱敏/审计/预算），且需先拍板 Q2 |
| 隐私 | 可承诺"零网络" | 需脱敏 + 数据出境决策；**Q2 未决前不启用** |
| 失败模式 | 覆盖率低（提不出新词） | 隐私/合规事故、成本失控、供应商变更 |

## 3. 现在就能用的能力（MVP 用法与范围）

### 3.1 命令速查

```bash
# 1) 默认 dry-run：只报告，不写盘，零网络（退出码 0=通过 / 2=门禁失败 / 4=前置失败）
python scripts/localize.py release

# 2) 机器可读
python scripts/localize.py release --json

# 3) 门禁通过后落盘 + 重建 + 回读校验（失败自动回滚词典并重建）
python scripts/localize.py release --apply

# 4) 只合并词典（不重建）；5) 词典结构体检
python scripts/localize.py merge --translations overlay.tsv --apply
python scripts/localize.py qa
```

本轮实测（我在本仓复跑）：

| 命令 | 结果 |
| :--- | :--- |
| `python scripts/localize.py release` | **exit 2**；761 候选 → 759 可加 / 2 隔离；2 个 H10 blocker；**0 文件变更、未创建 `.l10n/`**；词典 sha256 前后均为 `793905e9…` |
| `python scripts/localize.py qa` | **exit 0**；2,816 条存量体检 pass，0 finding |
| `python -m pytest tests/test_localize_mvp.py -q` | **46 passed**（1.80 s） |
| `python -m pytest -q` | **127 passed / 1 failed / 34 errors**（35 个 red 全部是沙箱 `%TEMP%` ACL 假阴性，含 1 failed 的 `test_escape_dollar`） |
| 生成物一致性 | 词典 **2,816** = 引擎内嵌 **2,816** = patcher 内嵌 **2,816**；README 计数门禁 **PASS**（2816 entries / 180 rules） |

### 3.2 MVP 只覆盖「Phase 0（部分）+ Phase 2 纵切」——边界必须说清

| 环节 | 状态 | 说明 |
| :--- | :--- | :--- |
| 候选 → 译文（provider 链：file > tm > cmd(低置信隔离) > online(拒绝)） | ✅ 已实现 | 真实数据走 `file`（候选自带译文） |
| QA 门禁 15/23 条规则 + 退出码语义 + `--waive` 留痕 | ✅ 已实现 | 未实现的 8 条每次报告都会列出 |
| 保序/最小 diff/CRLF/原子写/pre-merge 备份/失败回滚 | ✅ 已实现 | 有测试与独立验证 |
| 重建（只经 `build.py`）+ 回读校验 | ✅ 已实现 | 不手改生成物 |
| Phase 0：生成物对齐 2,816、README 计数对齐、门禁变绿 | 🟡 部分 | 引擎命中计数、`restore` 自动回归仍属 Phase 4 |
| Phase 1：提取器重写 / 探针 / D1 基线（SNR 0.21%→≥30%） | ⛔ 未做 | 仍用旧 761 条候选文件 |
| Phase 2 尾巴：`patterns.json` 生成与合并、H17–H20 | ⛔ 未做 | `merge` 只动 `zh-CN.json` |
| Phase 3：在线 provider（脱敏/审计/预算） | ⛔ 接口占位 | 无网络实现，任何情况下拒绝运行 |
| Phase 4：引擎命中/未命中计数器、`patch --dry-run`、客户端快照/自动回滚、真机验证 | ⛔ 未做 | **所以"关键路径 99%"目前无法验证** |
| Phase 5：跨 run 指标库（M16–M20） | ⛔ 未做 | 只有单轮 run 计数 |

> 一句话：**能自动的是"从候选文件到词典到生成物"这一段；"从客户端英文到候选文件"这一段（Phase 1）和"打补丁后到底好不好"这一段（Phase 4）还没有。**

## 4. 仍需人工的环节及原因

| 环节 | 为什么必须有人 | 现在的人工量 | 未来能否减轻 |
| :--- | :--- | :--- | :--- |
| 提供译文（新词） | TM 只能命中已见过的串；真实数据 TM 命中 **1/761**；在线 LLM 未启用 | 761 条全部来自人工维护的候选文件 | 部分：Phase 2 回填后 TM 覆盖率上升；Phase 3 可接在线（需拍板） |
| 片段语义（跨 text-node 拼接） | 引擎按单文本节点匹配；55/761（7.2%）是强片段信号，拼接后是否通顺**离线不可自证**（F9） | 需按上下文复核 | 只能靠 Phase 4 真机/运行时验证 |
| 上下文歧义（`Save`/`Cancel`/`Set up`） | 词典是单射，R3 无法根治 | 出现即人工裁决 | 仅缓解（引擎匹配语义一期不改） |
| 品牌/专有名词与术语表冲突 | 术语门禁只能查"必用词是否出现"，不能判断"该不该保留英文" | 2 条 H10 + 抽样 5 条风格问题 | 规则可细化；本质仍需人 |
| 原生菜单/对话框（8 组字面量） | 由 Electron 主进程绘制，只能逐条替换 | 每次客户端升级人工核对 | 否（随升级漂移） |
| 规则（`patterns.json`）审批 | 正则写错会影响整类文案；设计明确"不让 LLM 直写正则" | 每条人工接受/拒绝 | 可自动生成草案，仍需人批准 |
| closed Shadow DOM / canvas / webview / 跨域 iframe | 结构不可达（R1） | 永远英文 | 否 |
| 标题/文案的"信达雅" | R4：质量不可自证 | 抽样质检 | 否（只能抽样） |

## 5. 分阶段落地路线 P0 / P1 / P2

> 原则：每阶段**独立可交付、可回滚、可度量**；工期按「1 名熟悉仓库的开发者」估算。

| 阶段 | 对应 design Phase | 内容 | 退出标准（可验收） | 工期 |
| :--- | :--- | :--- | :--- | :--- |
| **P0 已完成 / 收尾** | Phase 0 部分 + Phase 2 纵切 | 生成物对齐 2,816、README 计数、离线 dry-run/apply/回滚管线、46 个测试、`.gitignore` 增 `.l10n/`、`.pytest_tmp/` | 生成物门禁绿（已验证）、README 门禁绿（已验证）、`localize qa` pass、dry-run 0 写盘（已验证） | 已完成 |
| **P0 待收尾（纯文档 + 2 条裁决）** | — | 修 F6/F2/RF-03 的文档披露（`CONTRIBUTING.md` 已补 F6 提示；`mvp.md` §11/§12 待补）；裁决 2 条 H10 术语冲突；修补 `mvp.md` 的 770→761、RF-04 等文档瑕疵 | 文档不再声称"apply 后 CI 自动全绿"；`release` 默认 dry-run 变绿（H10 修好后 exit 0） | 0.5 人日 |
| **P1 度量与采集** | Phase 1 + Phase 4 度量部分 | 提取器重写（词法扫描 + L1–L4 漏斗 + 代理字符安全）、D1 基线、引擎命中/未命中计数器、`restore` 自动回归、`patch --dry-run` | 真实客户端零崩溃、候选 ≤5,000、抽样 precision ≥30%、D1 条数固定；M1 可复算；`patch --dry-run` 与真打等价 | 3–5 人日（Phase 1）+ 2–3 人日（计数器/dry-run 等 Phase 0 欠账） |
| **P2 闭环与运营** | Phase 2 尾巴 + Phase 3/4/5 | 752 条存量回填、`patterns.json` 生成/合并 + H14–H20/H22、真机 V3 六路径验证、客户端快照/自动回滚、在线 provider（可选）、指标库 M16–M20 | M1 ≥95%、M2 ≥99% 且 P0 残留 0（真机）、回滚演练 3 次 ≤2 min、M4/M5 100%/≥99%、在线：20 个 payload 敏感命中 0、成本 ≤$1/版 | 2–3 周（含 Phase 3 可选 3–5 人日） |

### 5.1 每阶段的验收指标（只列可判定的）

| 指标（baseline/design 编号） | P0 现状 | P1 目标 | P2 目标 |
| :--- | :--- | :--- | :--- |
| M1 静态覆盖率（D1） | ≈78.9%（推算） | 可复算基线建立 | **≥95%** |
