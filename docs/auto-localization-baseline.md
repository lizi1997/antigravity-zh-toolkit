# Antigravity 全自动汉化：现状审计与“完美”可验收标准基线

> 文档定位：本文件是「全自动汉化」项目的第一份基线（baseline），只回答三件事：
> **现在已经自动化到什么程度 / 还差什么 / “完美”能不能被定义和验收**。
> 它不修改任何生产代码、词典或客户端；所有结论都可按「附录 A 复现命令」重跑。
>
> 审计时间：2026-11-24（Asia/Taipei）
> 审计对象：仓库 `antigravity-zh-toolkit`（v1.0.5 生成物）+ 本机已安装客户端
> 客户端实测：`Antigravity`（Electron 44.5.1，见 `engine/engine_template.js` 注释），
> `app.asar` 6.96 MB（已打补丁）、`app.asar.bak` 6.72 MB（官方备份）、`language_server.exe` 197.6 MB
>
> 结论一句话：**管线只有“引擎 + 打补丁 + 回滚”这三段是真正自动且可复现的；
> 提取是不可用的、翻译 100% 手工、验证（打补丁之后）为 0 自动化；“完美”只能被定义为
> “在显式声明的可达域内 100%”，全UI 100% 在技术上不可达、也不应作为验收目标。**

| J7 | “完美”可定义为：**可达域内静态界面 95%+、关键路径 99%+（P0 场景残留 = 0）、保真 100%、回滚 100%、无网络 100%**；全量 100% 必须显式声明为**不可达且不承诺** | 结论 |

## 2. 现状表：七个核心环节（+ 验证、分发两个扩展环节）的自动化程度

分级定义：**自动** = 单命令可重复执行且结果可判定；**半自动** = 脚本能跑但结论需人工判定或需人工搬运数据；**手工** = 无脚本支持；**不可用** = 有脚本但当前会失败或产出不可用。

| # | 环节 | 分级 | 工具入口 | 已自动化到什么程度 | 实测证据 | 阻断性缺口 |
| :- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **提取**（发现未译文本） | **不可用** | `scripts/extract_untranslated.py`；客户端 `Ctrl+Alt+L` | 静态：正则扫 `app.asar` + `language_server.exe` 及内嵌 ZIP；运行时：引擎把未命中串记入 localStorage，快捷键导出到剪贴板（≤1000 条，3 s 防抖） | 静态提取 **366,366 条**候选 / **364,400 条**“缺失” / 含空格 179,669 / 句子型 26,149；**写入 JSON 时 `UnicodeEncodeError`（孤立代理字符 `\ud800`）崩溃** | 无去噪、无归属（UI vs 源码/许可证/Rust 路径）、无优先级、无稳定输出；运行时导出纯手工 |
| 2 | **翻译**（英→中） | **手工** | 无（人写 JSON） | — | 全仓无任何 MT/LLM/翻译 API 调用（`scripts/*.py`、`engine/*.js`、`*.sh|bat|command` 扫描无 `urllib/socket/requests/fetch/XMLHttpRequest`） | 2,816 条词条与 180 条规则全部人工撰写；无量级扩展能力；质量依赖个人术语表 |
| 3 | **校验**（形式 / 数据 / 回归） | **半自动** | `scripts/build.py` 构建期断言；`pytest tests/`；CI `release.yml` | 形式校验自动：JSON 可解析、键无首尾空白、译文非空、禁哨兵、BOM 容错、`$` 转义、正则 flags 白名单；4 个测试文件共 58 个测试函数（参数化后 116 项）；CI 跑 pytest + `py_compile` + `node --check` + 生成物 diff + README 计数 | 本次实测 `pytest`：**80 passed / 2 failed / 34 errors**（其中 1 failed 与 34 errors 为沙箱临时目录 ACL 所致的假阴性；**1 failed 是真缺陷**：生成物只内嵌 2,792 条）；本地复跑 CI 的 README 计数门禁 → **FAIL** | 无占位符/URL/代码标识保真校验；无覆盖率门禁；无语义/准确率校验；无引擎运行时（jsdom/Electron）测试；门禁当前是红的 |
| 4 | **合并**（新词条 → 词典/规则） | **半自动** | `patcher.py` 的 `merge_dict_texts` / `merge_pattern_texts`；`seed_locale_files` | 运行期合并已自动且优先级明确：内嵌 < 随包 < 用户（按 key，后者胜）；规则按 `(pattern, flags)` 定位，用户新增规则置顶；首次安装自动 seed 可编辑词典 | 代码可读 + `test_audit_round2.py` 覆盖（本次因沙箱 ACL 未能执行，仅静态确认） | **“从提取结果到词典”没有任何自动通道**：人工从剪贴板/CSV 复制、手写译文、手改 JSON；无冲突检测、无去重、无「同英文不同上下文」建模 |
| 5 | **重建**（引擎 + 分发包） | **自动** | `python scripts/build.py [--no-exe]`；`build.bat/sh`；CI tag 触发 | 模板 + 词典 → 生成 `engine/ag_localization_engine.js` 与 `scripts/patcher.py`；`--no-exe` 跳过 PyInstaller；CI 在 tag/手动时矩阵构建 Win x64 + macOS arm64 并发布 | 生成逻辑完整；但**当前产物落后词典 24 条**（改动只提交了词典、没重跑构建） | 依赖人记得跑；无“词典变更即自动重建”的钩子；CI 只在 tag 上构建二进制，`main` 上不产出可分发包 |
| 6 | **打补丁**（注入客户端） | **自动**（需关客户端） | `python scripts/patcher.py patch` / `update`；`install.bat/sh`、`update.bat/sh`；`安装汉化.command`、`更新汉化.command`；单文件 exe；`watch` 常驻守望 | 目标文件 4 个：`dist/preload.js`（追加引擎）、`dist/menu.js`（2 组字面量）、`dist/updater.js`（2 组）、`dist/main.js`（4 组）；备份 + `.sha256` 边车；构建指纹（排除 4 个补丁目标）防跨版本回填；同目录临时文件 + `os.replace` 原子写；幂等（同引擎即 no-op）；词典变更时从官方备份重打；**运行中前置检查 + 排他锁 + 非 UTF-8 成员拒绝 + 文件 mode 保留** | 本机状态 `Patched: True`；代码路径完整；客户端运行时默认拒绝并提示先关闭（`--force` 可绕行） | **字面量漂移无自动修复**：客户端升级只要改一处引号/压缩风格，对应组即 `MISS`，仅打印告警不阻断；原生菜单/对话框只能靠硬编码替换 |
| 7 | **回滚**（还原官方） | **自动** | `python scripts/patcher.py restore`；`restore.bat/sh`；`还原官方.command` | 从 `app.asar.bak` 重写 `app.asar`（重算 integrity、原子写）；还原前比较构建指纹，**不一致默认拒绝（`--force` 放行）**；边车校验和不匹配**默认拒绝**；还原前自动存 `app.asar.pre-restore-<时间>` 副本 | 备份与边车均存在；还原路径可读 | **只有“回到官方原版”一条路**：无多版本快照、无“回滚到上一个汉化版本”、无自动触发（无健康检查）；备份丢失/损坏即失去回滚能力 |
| 8 | **验证**（打补丁之后） | **无（0 自动化）** | 无 | 仅人工：重启客户端 → 肉眼扫界面 → `Ctrl+Alt+L` 导出未译词 → 手工整理 | CI 无任何 UI 冒烟测试；引擎无“命中/未命中”计数；`tests/` 全部是 Python/静态断言 | **无法回答“这次汉化到底好了多少”**；无回归基线、无关键路径断言、无截图对比 |
| 9 | 分发 / 更新 | 半自动 | CI `release.yml`；`update` 一键命令；`watch` 常驻守望 | tag 触发矩阵构建、校验产物齐全、生成 `SHA256SUMS.txt`、创建 Release；客户端更新后双击 `update.bat` / `更新汉化.command` 即自动检测版本变化 → 刷新备份 → 重打（已是最新则 no-op）；`watch` 每 30 分钟检查一次，运行中自动跳过 | 缺失 Linux / macOS Intel；无编译后二进制冒烟测试（AUDIT F-D4-04） | 新词条仍需走 `localize` 管线入库（`update` 只重打已有词典）；无自动更新通道（需手动跑一次或挂开机任务） |

### 2.1 当前“发一次新版汉化”的真实人工步骤（约 10 步）

1. 打开客户端逐屏找英文 → 2. `Ctrl+Alt+L` 导出 → 3. 粘贴到编辑器去重 → 4. 手写/润色译文 → 5. 手工判重（大小写、单复数、句中片段）→ 6. 手改 `locales/zh-CN.json` / `patterns.json` → 7. 关闭客户端 → 8. 跑 `python scripts/build.py --no-exe` → 9. 跑 `python scripts/patcher.py update`（`patch` 的超集：自动识别客户端更新并刷新备份，已是最新则 no-op）→ 10. 重开客户端肉眼验收（漏译再回到第 1 步）。

> 其中只有第 8、9 步是命令；第 1–7、10 步全是人工。**这就是“现在自动化到什么程度”的准确答案：约 2/10。**

### 2.2 覆盖率现状估算（可复算，但分母有前提）

| 口径 | 分子 | 分母 | 结果 |
| :--- | ---: | ---: | ---: |
| 已知静态 UI 全集（人工盘点口径） | 2,816（词典已收） | 2,816 + 752（待补译）= 3,568 | **78.9%** |
| 计入规则覆盖（180 条动态文案无法逐条计数） | 不可量化 | 不可量化 | 无法给出可信百分比 |
| 运行时真实命中率 | 无计数器 | 无计数器 | **当前无法测量** |
| 静态提取口径（错误口径，仅作反例） | 2,816 | 364,400 + 2,816 | 0.77% → 说明提取器输出**不能**当分母 |

> 反例价值：自动提取的 364,400 条里，真正 UI 文案约 752 条 → **信噪比 ≈ 0.21%**，噪声放大约 480 倍。
> 因此“用静态扫描穷举 UI 字符串全集”这条路在工程上不成立。

## 3. 硬边界清单（与证据）

**硬边界** = 不管做多少工程优化，当前架构（Electron 渲染层 DOM 注入）都无法覆盖或无法可靠覆盖的区域。

| # | 边界 | 为什么不可达（机制） | 证据 | 是否有替代路径 | 残余风险 |
| :- | :--- | :--- | :--- | :--- | :--- |
| B1 | **closed Shadow DOM** | `element.shadowRoot` 对 closed 模式返回 `null`；引擎只能递归开放 shadow root | `engine_template.js` 仅用 `root.shadowRoot` / `node.shadowRoot` 判断 | 需 `attachShadow` 打桩（污染宿主 JS）或 CDP 层拦截，均超出现有架构 | 组件库越新、越倾向 closed，则漏译面越大 |
| B2 | **canvas / 图片文字** | 文本不以 DOM 节点存在，无 `nodeValue` 可替换 | 引擎无 canvas/OCR/图像处理代码（全量扫描确认） | 需 OCR + 覆盖层，破坏像素级一致性 | 图表、截图、视频封面 |
| B3 | **webview 内容** | guest 页面是独立渲染进程/文档，不在 `document.body` 树内 | 引擎无 `webview`/`contentWindow`/`contentDocument` 引用 | 需在 guest preload 里再注入一份引擎（当前无 preload 钩子） | 内置浏览器面板内英文 |
| B4 | **跨域 iframe** | 同源策略禁止访问 `contentDocument` | 同上（引擎完全未处理 iframe，**同源 iframe 也不处理**） | 同源 iframe 可另注入；跨域不可行 | 预览面板、嵌入式第三方页 |
| B5 | **原生系统对话框 / 菜单** | 由 OS/Electron 主进程绘制，不是 DOM | 只能改 `dist/menu.js`（2 组）、`dist/updater.js`（2 组）、`dist/main.js`（4 组）字面量 | 可以继续逐条加字面量替换（脆弱、随版本漂移） | 文件选择框、系统通知、Dock 菜单、右键菜单、Electron 默认菜单（File/Edit/View/Window/Help 未译）、权限提示 |
| B6 | **远程/服务端下发内容** | 文案在服务端渲染或按实验开关下发，客户端升级之外也会变 | `UNTRANSLATED_UI_STRINGS.md` 大量 `language_server.exe!main.js` 条目（735 条）来自服务端 UI 包 | 只能靠运行时兜底 + 词库外挂；无法在上游修复 | 新功能灰度即出现英文，且不进任何发布清单 |
| B7 | **跨文本节点碎片** | 引擎按**单个 text node** 匹配；一句话被 `<span>/<b>/<a>` 切开后每段独立查表 | 词典中 36 个键以 `:` 结尾、26 个以 `…` 结尾、2 个以 `,` 结尾、4 个以 `(` 开头，另有 129 个键以小写字母开头（片段形态）；存量候选里 47 条为句中断片（如 `to be installed.`、`icon in the URL bar.`） | 需上下文拼接/父节点级匹配（会引入误伤） | 长句、富文本说明、带内联链接的提示 |
| B8 | **动态变量** | 精确匹配无法命中含变量文本；只能靠正则 | 180 条规则中 175 条靠 `$n` 捕获；**95 条不含 `\d`**（即文本型变量）→ 变量形态一变即漏 | 规则可扩，但每条都要人工写；无模板从翻译结果自动生成 | 倒计时、用户名、路径、模型名、数字格式（`1,234` vs `1234`） |
| B9 | **超长文本** | 引擎硬阈值 `trimmed.length > 500` 直接跳过 | `engine_template.js` `translateText()` | 提高阈值即可，但长文本多为模型输出/文档正文（见 R3） | 长段说明文永远英文 |
| B10 | **已含中文的混合串** | 只要文本含任一 CJK 字符即整段跳过 | 同上（`/[一-鿿]/`） | 可改为按片段处理 | 「中文 + 英文术语」混排提示不翻译 |
| B11 | **离线 / 隐私约束** | 工具承诺零网络请求；引擎在沙箱 preload 中无 `fs` | 全仓无网络调用（实测扫描）；`require('fs')` 在渲染进程抛错（引擎注释） | 若引入在线 MT，则破坏“零网络”承诺；本地小模型可替代但体积/性能不可行 | 任何“在线自动翻译”方案都需先修改隐私承诺 |
| B12 | **客户端升级后的选择器/字面量漂移** | 补丁靠固定成员名（`dist/preload.js` 等）与固定英文字面量；引擎跳过区靠 class 名（`monaco-editor`/`CodeMirror`/`cm-editor`/`view-lines`/`xterm`/`terminal`） | `patcher.py` `PATCH_TARGETS` + `patch_menu_js`/`patch_main_js`/`patch_updater_js`；`isSkipElement()` | 需指纹库/多版本适配 + 升级后自动回归（当前都没有） | 升级后“部分汉化 + 跳过区失效（代码被翻译）” |
| B13 | **运行时热更新** | 沙箱 preload 无 `fs`，外部词典读不到 | 引擎注释与 `nodeFs()` 实现；README 已声明 | 只能重新打补丁 | 改词必须重打补丁（一次约 1 次安装动作） |

## 4. 可衡量验收标准（含“100% 完美不可达”的形式化说明）

### 4.1 为什么“100% 完美”不可达（四条硬理由）

| 理由 | 说明 | 对本项目的含义 |
| :--- | :--- | :--- |
| **R1 表示不可达** | B1–B5：closed Shadow DOM、canvas、webview、跨域 iframe、原生对话框/菜单根本不在 DOM 可达集合内 | 可达集合 ≠ 全集，且**永远不会相等**（除非改架构为原生层/OCR 混合） |
| **R2 全集不可枚举** | 实测：自动提取 364,400 条“缺失”，真值约 752 条（SNR 0.21%）；服务端下发（B6）还会随时新增 | 无法构造可信分母 → “覆盖率 100%”在定义上不可判定 |
| **R3 上下文不可判定** | 同一英文串在不同上下文需不同中文（`Save` 动词/名词、`Cancel` 取消/撤销、`Open` 打开/开启）；词典是 `key→value` 单射，**无法表达上下文** | 存在必然错译点；任何单一映射方案都有上限 |
| **R4 质量不可自证** | 译文正确性需语义判断；本地规则/正则只能校验形式（占位符、标点、术语），不能校验“信达雅” | “准确率 100%”不可自动证明，只能抽样统计 |

> 另外还有 2 个**工程现实**：客户端升级会让任何版本闭包失效（B12）；分布式修改官方包天然存在「完整性校验/签名」的对抗成本（见 §5 R5）。
>
> **结论：把“完美”定义成“全 UI 100% 中文”是不可验收的伪目标。可验收的“完美”必须是
> 「在显式声明的可达域 D 内、以可复现方式达到 100%，并对 D 之外给出明确不覆盖声明」。**

### 4.2 建议的可达域定义（D）

- **D1 静态界面**：主文档 DOM 文本节点 + 11 个可译属性（`placeholder`/`title`/`aria-label`/`aria-description`/`aria-placeholder`/`data-tooltip`/`tooltip`/`data-tip`/`data-title`/`data-placeholder`/`alt`）+ `input[type=button|submit|reset]` 的 `value` + 开放 Shadow DOM。
- **D2 关键路径**：首启/引导、登录与账户、设置-权限、对话与工具调用、审批弹窗（读/写/执行/沙箱外）、退出确认，共 6 条路径。
- **D3 动态文案**：由 180 条正则 + 自动生成的模板覆盖的带变量文案。
- **D4 原生层**：仅限 `menu.js`/`updater.js`/`main.js` 中已建立字面量映射的 8 组（2+2+4）。
- **显式不覆盖**：B1–B6、B9、B10 中的全部内容；跨境/系统级 UI 一律不承诺。

### 4.3 验收指标（可直接落成门禁）

| ID | 指标 | 定义 / 公式 | 测量方法 | 当前基线 | 目标（一期） | 目标（二期） | 门禁 |

## 5. 风险与不适用场景

### 5.1 风险登记（按“会不会静默吃掉用户成果”排序）

| ID | 风险 | 触发条件 | 影响 | 现有缓解 | 结论 |
| :- | :--- | :--- | :--- | :--- | :--- |
| R1 | **词典改了但没重建 → 生成物落后** | 只提交词典 | 新词条不进客户端；CI 门禁红 | 无自动钩子 | **已实际发生**（差 24 条），需在流水线中前置重建 |
| R2 | **提取器崩溃/污染** | 客户端含 `\udXXX` 转义或大量源码字符串 | 产出不可用；若误写入 `locales/` 会渲染空文案 | 无 | 已实测崩溃，必须先重写提取器再谈自动化 |
| R3 | **误伤用户/模型文本** | 聊天正文、错误堆栈、按钮同形词 | 用户内容被“翻译”篡改（如消息正文恰好是 `Default`） | 跳过 PRE/CODE/TEXTAREA/编辑器 | DOM 全量替换天然有此风险；需要“按区域生效”策略 |
| R4 | **跳过区失效导致代码被翻译** | 客户端升级改了编辑器 class 名 | 代码显示被中文替换（严重） | class 名硬编码 | 高影响低概率，需升级回归用例 |
| R5 | **完整性/签名冲突** | macOS 代码签名、Electron `asarIntegrity`、企业 MDM 校验 | 客户端拒绝启动或被安全软件拦截 | 原子写 + 备份 | macOS 用户是主要风险面；需明确“非官方支持”声明 |
| R6 | **回滚能力单点** | 备份被删/被替换/跨版本 | 只能重装客户端 | 边车校验和、指纹比对（仅告警） | 建议多版本快照 + 还原前自动校验 |
| R7 | **隐私外泄** | 未译采集把用户输入/提示词写入 localStorage 并导出 | 用户隐私风险 | 仅本地、上限 1000 条、手动导出 | 需采集端过滤（跳过输入区、聊天正文） |
| R8 | **性能退化** | DOM 极大（长对话/大文件树） | 每 2 s 全量 TreeWalker 卡顿 | 无节流上限 | 需实测预算（M15） |
| R9 | **“一半中文”体验** | 部分覆盖 | 比全英文更难读、更招投诉 | 无 | 必须用覆盖率门禁换取“可发布” |
| R10 | **法务/合规** | 分发修改后的官方包或附带的词典被视为衍生作品 | 下架/追责 | MIT + 免责声明 + 不发布 app.asar | 预翻译与词典分发都需评审 |
| R11 | **翻译质量不可自动化证明** | 追求“100% 准确率” | 无休止返工 | 抽样 + 人工复核 | 用 M4/M5/M7 量化，别承诺准确率 100% |
| R12 | **自动化引入新耦合** | 自动改词典/自动打补丁 | 一次错误配置批量污染 2,800 条 | 无 | 需要“生成物可 diff、可回滚、可丢弃”的设计 |

### 5.2 不适用场景（明确不支持）

| 场景 | 原因 |
| :--- | :--- |
| 非中文目标语言 | 引擎与词库为 zh 专用；`currentLang` 仅 `zh`/`en` 两态切换 |
| 非 Antigravity / 非 Electron 客户端 | 补丁目标（`dist/preload.js` 等）与 DOM 结构强绑定 |
| `language_server` 内部（Go 服务端）文本 | 不在渲染层 DOM 内；只能靠其自身 UI 包（B6） |
| 需要操作系统级菜单/对话框全汉化 | 只能改 Electron 主进程字面量，系统原生组件不可达（B5） |
| 强完整性校验/受管设备（MDM） | 改包会被拒绝或告警（R5） |
| 无写入权限的安装目录 | 原子写失败，仅提示关闭客户端（权限问题无法绕过） |
| 需要“实时翻译任意网页/任意用户内容” | 超出本项目范围，且与隐私承诺冲突（R7/M13） |
| 要求“零人工介入的绝对 100%” | R1–R4 决定不可达（§4.1） |

## 6. 结论：给下游三个可执行判断

1. **“完美”可以定义，但必须带定义域**：可达域 D1–D4 内可验收（静态 95%+/关键路径 100%/保真 100%），D 之外必须写成不覆盖声明。任何承诺“全 UI 100%”的方案在评审阶段就应被否决。
2. **自动化瓶颈不在“翻译”，而在“度量”**：真正卡住自动化的是三件事——提取器不可用（R2）、没有运行时命中计数（M2/M6 不可测）、没有 “词典→产物→客户端” 的单向一致门禁（R1）。这三项不补齐，接任何自动翻译都只是把手工搬到别处。
3. **最能立刻拿到确定收益的是“把红门禁变绿 + 建立可测量基线”**：修复生成物 24 条漂移、让 README 计数门禁通过、给引擎加命中/未命中计数器、把 `restore` 纳入自动回归。这四项的收益是确定的，成本远低于架构改造。
